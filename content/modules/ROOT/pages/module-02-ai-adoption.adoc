= AI Adoption

[[sovereign-ai-overview]]

== AI on OpenShift 5

OpenShift 5 is where the AI workload and the data can stay together. In this module you use the agentic features from OpenShift 5: Lightspeed troubleshooting, agentic update analysis, an OpenShift MCP server, and the MCP gateway in Red Hat Connectivity Link. You then run a notebook on Red Hat OpenShift AI so the data science work stays on the cluster you manage.

The OpenShift 5 First Look lab preloads broken sample applications, an `mcp-cli` client, and mock MCP servers. This environment does not. Each section uses that product path first. When a component is not installed, you do the same task with OpenShift Lightspeed or `oc` against the virtual machines from Module 1.

[[agentic-troubleshooting]]
== Agentic troubleshooting

Agentic troubleshooting uses OpenShift Lightspeed and the agentic operator. You can start an investigation yourself in the chat, or let a critical alert start one. A person still approves any change the agent wants to make.

=== Before you begin

. Check whether Lightspeed and the agentic operator are installed:
+
[source,role="execute"]
----
oc get pods -n openshift-lightspeed
----
+
. In the OpenShift console, open *Observe* -> *Alerting*.
. Select *All Projects* and clear the *Platform* filter so application alerts are visible.
+
image::agentic-troubleshooting-remove-platform-filter.png[Alerting view with the Platform filter cleared,link=self,window=blank,width=100%]
+
image::agentic-troubleshooting-observe-alerting.png[Alerting view in the OpenShift console,link=self,window=blank,width=100%]

[NOTE]
====
If `openshift-lightspeed` does not exist, or the Lightspeed icon is not in the console, keep going. Use *Observe* -> *Alerting* and the `oc` checks in each exercise. The investigation steps are the same.
====

=== Investigate a workload

. Open *Observe* -> *Metrics* and run this query to see which pods are using CPU:
+
[source,role="copypaste"]
----
topk(10,
  sum by (namespace, pod) (
    rate(container_cpu_usage_seconds_total{container!="",pod!=""}[5m])
  )
)
----
+
image::agentic-troubleshooting-metrics-console.png[Metrics query in the OpenShift console,link=self,window=blank,width=100%]
+
. Open OpenShift Lightspeed from the chat icon and select *troubleshooting* mode.
+
image::agentic-troubleshooting-mode-selector.png[Lightspeed mode selector set to troubleshooting,link=self,window=blank,width=100%]
+
. Paste this prompt:
+
[source,role="copypaste"]
----
Investigate the health of virtual machine rhel9-lab-vm and any firing application alerts on this cluster. Correlate pod status, events, and metrics. Do not delete or power off rhel9-lab-vm or rhel-webserver.
----
+
. If Lightspeed asks to approve a tool such as `pod_exec`, click *Approve*. A failed exec does not end the investigation. Lightspeed can still use logs, events, and metrics.
+
image::agentic-troubleshooting-tool-approval.png[Tool approval prompt in Lightspeed,link=self,window=blank,width=100%]
+
. Ask a follow-up:
+
[source,role="copypaste"]
----
Identify recent changes that may have caused a problem and suggest remediation. Do not apply any change.
----
+
. Read the mitigation plan. Leave it unapplied.
+
image::agentic-troubleshooting-mitigation-plan.png[Mitigation plan in the Lightspeed reply,link=self,window=blank,width=100%]

=== Investigate a firing alert

. If a warning or critical alert is firing, paste this prompt and replace the alert name:
+
[source,role="copypaste"]
----
Investigate the root cause of the firing <alert-name> alert. Use cluster state, pod logs, and metrics. Do not change the cluster.
----
+
. If nothing is firing, paste this instead:
+
[source,role="copypaste"]
----
List the highest severity alerts on this cluster, including pending alerts. Say whether rhel9-lab-vm or rhel-webserver is affected. Do not change the cluster.
----

=== Build a chart for the investigation

. Open *Observe* -> *Dashboards (Perses)* and create a dashboard named `Investigation Hub`.
+
image::agentic-troubleshooting-create-dashboard.png[Create a Perses dashboard,link=self,window=blank,width=100%]
+
. In Lightspeed troubleshooting mode, paste:
+
[source,role="copypaste"]
----
Which pods are using the most CPU? Show me the top 5. Use Prometheus and visualize.
----
+
. If a chart appears in the chat, use *Add to dashboard* to put it on `Investigation Hub`.
+
image::agentic-troubleshooting-perses-inline.png[Chart rendered in the Lightspeed chat,link=self,window=blank,width=100%]
+
image::agentic-troubleshooting-add-to-dashboard.png[Add to dashboard on an inline chart,link=self,window=blank,width=100%]

[NOTE]
====
If *Dashboards (Perses)* is not in the menu, keep the chart in the chat reply and continue.
====

=== Let an alert start the investigation

The alerts adapter can open an AgenticRun for a critical alert. Analysis can be automatic. Execution stays manual.

. See whether the agentic policy and adapter are installed:
+
[source,role="execute"]
----
oc get approvalpolicy cluster
oc get configmap alerts-adapter-config -n openshift-lightspeed
----
+
. If both exist, allow automatic analysis and turn on critical alerts:
+
[source,role="execute"]
----
oc patch approvalpolicy cluster --type merge \
  -p '{"spec":{"stages":[{"name":"Analysis","approval":"Automatic"},{"name":"Execution","approval":"Manual"},{"name":"Verification","approval":"Automatic"}]}}'
oc get configmap alerts-adapter-config -n openshift-lightspeed -o json \
  | jq '.data["config.yaml"] |= gsub("# +- critical"; "    - critical")' \
  | oc apply -f -
----
+
. Open the *Agentic Runs* view. A new run moves from *Analyzing* to *Proposed*.
+
image::agentic-troubleshooting-agentic-runs-list.png[Agentic Runs list,link=self,window=blank,width=100%]
+
. From the terminal:
+
[source,role="execute"]
----
oc agentic run list
----
+
. Open a run in the *Proposed* phase and read the plan. Do not execute a remediation that changes `rhel9-lab-vm` or `rhel-webserver`.

[NOTE]
====
If `approvalpolicy` or `alerts-adapter-config` is missing, skip the patches. The troubleshooting chat you already ran is the same investigation, started by you instead of by an alert.
====

=== Verify

* You can point to a Lightspeed reply, or to an alert in *Observe* -> *Alerting*, that describes the state of this cluster
* `rhel9-lab-vm` and `rhel-webserver` are still running

[[agentic-updates]]
== Agentic updates

OpenShift 5 can score a cluster before an update. The Cluster Update page runs that analysis as an AgenticRun. The same page also has Lightspeed buttons for a pre-check, update status, and troubleshooting. Those buttons open a chat with the prompt already filled in.

. Open *Administration* -> *Cluster Settings* and find the update or cluster update view.
+
image::agentic-updates-cluster-update-page.png[Cluster update page,link=self,window=blank,width=100%]
+
. If an *Analyze* button is shown for an available path, select a path in the current channel and click *Analyze*. Wait for the recommendation and read the risk level. Do not start the update.
+
image::agentic-updates-analyze-button.png[Analyze button on an update path,link=self,window=blank,width=100%]
+
. If *Analyze* is not shown, open Lightspeed and paste:
+
[source,role="copypaste"]
----
Is this cluster ready for the next update in the current channel? Check ClusterOperators, firing alerts, and deprecated APIs. Do not start an update.
----

=== Verify

[source,role="execute"]
----
oc get co
oc get clusterversion version -o jsonpath='{.status.desired.version}{"\n"}'
----

* ClusterOperators are listed
* You have a recommendation, from *Analyze* or from Lightspeed, and you did not start an update

[[mcp-server]]
== MCP server

A Model Context Protocol (MCP) server exposes cluster APIs as tools an agent can call. The OpenShift MCP server toolsets include core resources, Prometheus metrics, kubeconfig contexts, node network diagnostics, and OpenShift Service Mesh. This lab does not install the service mesh sample or the `mcp-cli` pod from OpenShift 5 First Look. Use Lightspeed, which calls those tools for you. If the MCP server is installed, the same prompts work against it.

. Check for the server:
+
[source,role="execute"]
----
oc get pods -n openshift-mcp
----
+
. Open OpenShift Lightspeed and paste:
+
[source,role="copypaste"]
----
List the pods that belong to virtual machine rhel9-lab-vm. Include the namespace, readiness, and restart count. Do not delete anything.
----
+
. Ask for logs from one of those pods:
+
[source,role="copypaste"]
----
Show the recent logs for the virt-launcher pod of rhel9-lab-vm. Quote any error you find. Do not restart the pod.
----
+
. Ask Lightspeed to create a ConfigMap. If it only prints YAML, apply that YAML yourself.
+
[source,role="copypaste"]
----
Create a ConfigMap named test-config in namespace default with key app.properties and value environment=staging
----
+
. Confirm it, then remove it:
+
[source,role="execute"]
----
oc get cm test-config -n default -o yaml
oc delete cm test-config -n default
----
+
. Ask for a metric query and for the virtual machine vulnerabilities you reviewed in Module 1:
+
[source,role="copypaste"]
----
Which pods are using the most memory right now? Use Prometheus.
Query Red Hat Advanced Cluster Security for vulnerabilities in virtual machine rhel9-lab-vm. If that virtual machine has no results, query rhel-webserver. Do not change either virtual machine.
----

=== Verify

* Lightspeed listed pods for `rhel9-lab-vm`, or you confirmed the virtual machine with `oc get vm -A`
* `test-config` is gone: `oc get cm test-config -n default` reports that it was not found
* You have a vulnerability summary for one of the virtual machines

[[mcp-gateway]]
== MCP gateway

The MCP gateway in Red Hat Connectivity Link publishes several MCP servers through one endpoint. Keycloak authenticates the caller. Policy decides which tools that caller can use, and the gateway can limit the rate per user. The backend servers stay unchanged.

OpenShift 5 First Look registers three mock servers, `inventory`, `payments`, and `accounts`, behind that gateway. This lab does not. Keycloak is already the identity provider here. Use it as the same kind of control the gateway puts in front of MCP tools.

. In the OpenShift console, look for *Connectivity Link*.
. If it is there, open *Overview* for all projects, then open *Policy Topology*.
+
image::mcp-gateway-connectivity-link-overview.png[Connectivity Link overview,link=self,window=blank,width=100%]
+
image::mcp-gateway-connectivity-link-topology.png[Connectivity Link policy topology,link=self,window=blank,width=100%]
+
. Check the cluster for a gateway and for registered MCP servers:
+
[source,role="execute"]
----
oc get pods -A | grep -E 'kuadrant|mcp-gateway|mock-mcp|openshift-mcp' || true
oc get route -A | grep -E 'mcp-gateway|mcp-server' || true
----
+
. Ask Lightspeed:
+
[source,role="copypaste"]
----
Is an MCP gateway from Red Hat Connectivity Link configured on this cluster? If it is, list the registered MCP servers and the identity provider used to call them. Do not create tokens or change Keycloak.
----

=== Verify

* You know whether *Connectivity Link* is installed
* You can describe the three controls the gateway adds: authentication, which tools a caller may use, and one endpoint in front of several MCP servers

== Deploying a Jupyter Notebook

Let's create a Jupyter notebook server to explore the OpenShift AI dashboard.

.Procedure
. To create a Jupyter notebook server, click on *Applications* -> *Enabled* -> *Start basic workbench*
+
image::04-openshift-ai-dashboard-04.png[Create Jupyter Workbench, width=100%, link=self, window=blank]
+
+
. Configure your workbench:
.. Select a notebook image *Jupyter | Data Science | CPU | Python 3.12 | 2025.2*
+
[IMPORTANT]
====
Notice the accelerators location that are not available for the notebook image. If your cluster had access to GPU, you would be able to select the GPU accelerator. You can also use environment variables to configure access to your storage/databases
====
+
image::04-openshift-ai-dashboard-045.png[Configure Jupyter Workbench, width=100%, link=self, window=blank]
+
image::04-openshift-ai-dashboard-05.png[Configure Jupyter Workbench, width=100%, link=self, window=blank]
+
.. Click *Start Workbench* to launch your notebook server
+
image::04-openshift-ai-dashboard-06.png[Start Workbench, width=100%, link=self, window=blank]
+
. Once your notebook server is running, click *Open in a new tab* to access your Jupyter environment (if you get prompted to log in, use Username: `admin` and Password: `{openshift_cluster_admin_password}`):
+
image::04-openshift-ai-dashboard-06.png[Jupyter Notebook Server Running, width=100%, link=self, window=blank]
+
. Once your notebook server is running, click *Open in New Tab* to access your Jupyter environment.
. Your Jupyter notebook interface opens in a new tab. You can create notebooks, upload files, use a terminal, or open an existing `.ipynb` file.
+
image::04-ai.png[Jupyter Notebook, width=100%, link=self, window=blank]
+
. Next, you will run the *Python Artificial Intelligence Projects for Beginners* sample from this https://github.com/mfosterrox/Python-Artificial-Intelligence-Projects-for-Beginners[repository] (`Student performance.ipynb` and the CSV data files in the same folder) in your workbench:
.. Open a terminal: from the *Launcher* (or the *File* menu), choose *New* → *Terminal*.
.. Clone the repository into your workbench (one block to copy and paste):
+
[source,bash,role=execute]
----
git clone https://github.com/mfosterrox/Python-Artificial-Intelligence-Projects-for-Beginners.git
----

.. In the Jupyter *file browser* (folder icon or Jupyter logo), open *Python-Artificial-Intelligence-Projects-for-Beginners*, then double-click *Student performance.ipynb* to open it.
.. Run the notebook: menu *Run* → *Run All Cells*, or run each cell in order with *Shift+Enter*.
+
You should see the output of the notebook in the terminal, along with the final plot of the student performance.
